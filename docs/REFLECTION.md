# SmartSurvey: AI4SE 智能体软件工程实践与反思报告

## 1. 项目概述与 Superpowers 开发全景 (Project & Workflow Overview)

SmartSurvey 是面向科研人员的中文学术综述全自动编译器：用户上传一篇或多篇学术 PDF，系统自动完成「解析 → 学术矩阵提取 → 证据约束校验 → 文献库关系建模 → LaTeX/Word 综述全文生成」的完整闭环。它属于非 harness 的 B 类应用——不是教科书式的脚手架演示，而是承载真实业务价值、需要物理编译器与外部 LLM API 深度协作的工程系统。

整个开发流程严格以 Superpowers 技能框架为主线，历经 Phase 1 至 Phase 9 七个阶段，收敛为四个可独立验证的能力域：从零搭建的基建层（测试框架与依赖基线）、五大核心模块（`pipeline`、`graph`、`synthesis`、`credentials`、`agent`）、OS Keyring 凭据托管与无头 CI 集成、以及自愈 RAG 管道与 2D 交互式知识图谱。数据支撑上，全量测试套件达到 115 个用例（115/115 Passed，0 回归），实现了真正的 TDD 驱动——没有一次绕过红灯直通绿灯的书写。

值得强调的是，本项目将「证据包含校验（Evidence Gate）」作为不可触碰的学术红线贯穿始终，最终达成 100% 零丢纸（Zero-Drop）保证：任何一篇被解析的论文，都保证被写入最终产物，绝不允许被静默丢弃。

## 2. Superpowers 方法论与技能框架的批判性评估 (Methodology Assessment)

**发挥最大作用的技能**有三：**`brainstorming`**（头脑风暴）是开发前最强有力的「刹车」。它在书写任何代码之前强行拦截，通过苏格拉底式逐问，逼出了几个事后证明决定架构走向的核心边界——「双层 Schema」（学术矩阵的通用/领域分层）、「防止空气警告（Evidence Gate）」（杜绝证据丢失的静默降级）、以及「纯文本 LaTeX 输出」（回归测试易于断言，规避物理排版不确定性）。**`subagent-driven-development`**（子 Agent 驱动）：随着 Phase 6 进入后期重构，主会话上下文已近膨胀阈值，将相互独立的子任务（图谱重构、视觉回归）派发给「新鲜子 Agent」，既降低了 Context Bloat，也带来更客观的第二视角。**`systematic-debugging`**（系统化调试）：排查「多文档页码冲突」与「LaTeX 编译崩溃」时，强制我遵循「定位根因 → 提出假设 → 最小复现 → 验证修复」四阶段，杜绝盲目猜改，并最终将两起故障都溯源到规约层缺陷而非实现层笔误。

**「形式大于实质」的技能与反思**：并非所有投入都等价。其一，频繁切换 Git Worktree 在仅 2 分钟的微小程序性修复上，带来了不成比例的上下文切换与分支开销，属于「为隔离而隔离」。其二，早期过度依赖静态字符串语法扫描（`validate_latex_syntax` 的栈式括号配对校验），忽视了物理编译器（xelatex）真实运行时的报错——前者只能发现「形」的失衡，后者才能暴露「实」的崩溃，导致前期产生了一批「为了规约而规约」的无效约束。

**最佳任务颗粒度与子 Agent 自主上限**：实践经验收敛出的最佳任务粒度为 2~5 分钟，且必须包裹 1 个明确的 TDD 红绿循环（一个红灯观察 + 一次绿灯确认）。在此颗粒度下，子 Agent 在无需人类介入的前提下，最多可自主连续推进 3~4 个子 Task（约 15~20 分钟）而不偏离主题；超过该上限后，偏差累积的风险显著上升，必须引入人工审查检查点。

## 3. TDD 强纪律在 AI 协作中的双面效应 (TDD: Obstacle or Amplifier?)

**核心论点：TDD 是 AI 协同开发中最坚固的「安全阻退阀」与「放大器」。** 对传统开发者，TDD 常被视为时间开销；但对大模型而言恰恰相反——红灯测试是模型与代码之间唯一可自动裁定的「真值锚点」，它把「模型说改好了」这一不可靠的口头承诺，替换为「pytest 说通过了」这一可验证的客观事实。

**案例 1（FakeKeyring）**：实现 OS 钥匙串托管（Task 22.1）时，我们手写 `FakeKeyring` 单测替身，模拟 `keyring.set_password/get_password` 语义并注入 `CredentialStore`。在未触碰真实 OS API 之前，红灯先行即锁定了「单键 JSON 存储」的序列化格式与 `Migration Guard` 平滑迁移的幂等逻辑——换行、Unicode、空键等边界无需真实钥匙串守护进程即可 100% 确定性验证。这是用确定性替身换取确定性。

**案例 2（StatefulMockExtractor）**：实现「幻觉自愈重试环路（Task 16.1）」时，我们构造携带内部状态转移的 Mock Extractor：首次调用返回非法 JSON（模拟幻觉），第二次返回合法 JSON（模拟反馈后修正）。在**不消耗一分钱网络 API** 的前提下，毫秒级验证了「首诊失败 → 注入 XML 反馈 → 二诊自愈」的完整状态机转移。直接联调真实 LLM 单次成本数百 Token 且结果不确定；替身在把成本归零的同时把不确定性冻结为确定性，极大节省了开发期 Token 预算。

## 4. SPEC/PLAN 规约质量对实现质量的影响案例 (Case Studies on Spec Quality)

**案例 A（规约模糊导致的偏离）**：早期多论文批量提取时，`SPEC.md` 未定义「多文档页码命名空间」——「第 5 页」到底属于哪篇论文。结果代码采用全局 `page_texts.update()` 覆盖方案，使所有论文共享「最后写入者胜」的页码文本；后置证据匹配时，`Costanzino` 等先提取的论文因失联而被 **100% 静默误杀（Blocked）**——调用链看似成功，实际却丢失整篇论文，这是最危险的一类失败（无异常、无报错）。

**重构与改进**：我们立即修正了 `SPEC.md` §20.2，提出 **Inline Scope Binding（进程级物理绑定）** 规约：将证据包含校验从「标题匹配」改为「物理绑定」——即在校验循环内，通过当前循环 `paper` 对象的 `page_text_by_number()` 方法，把包含校验死死锁定在**当前论文对象的单页域内**，从根本杜绝跨论文误伤。这一规约补齐后，实现了 Zero-Drop 零丢纸保障，且配套了 `test_pipeline.py` 的 Zero-Drop 回归用例，将「损失被静默吞掉」这个漏洞永久封死。

**案例 B（格式边界不清）**：LLM 驱动生成综述正文时经常泄露 `(evidence_page=2)` 这类 RAG 检索元标记，破坏交付物的学术整洁度。我们未把信任寄托于提示词——而在 `SPEC.md` §22.2 追加「双重保险规约」：第一道防线是系统提示词约束（告知模型不输出检索元数据），第二道是 Python 端 `re.sub` 正则后处理器（在 `synthesis.py` 导出端强制清洗）。两道防线互为冗余，即便提示词被无视，正则也能兜底。「提示词 + 代码双保险」此后成为整个项目防御性设计的模板。

## 5. 凭据安全存储、无头 CI 与分发工程考量 (Credentials & Distribution)

**凭据安全（§3.1 / §9.1）**：项目彻底抛弃了明文 `.env` 硬编码，而采用 Python `keyring` 库将 API Key、Base URL 与 Model Name 序列化为单一 JSON 写入操作系统加密钥匙串，UI 侧边栏提供密码遮罩（`type="password"`）与一键清除入口，并遵守 `§9.2` 的所有禁止行为（不落 Git、不外显、不进镜像）。

**三级回退链（Three-Level Fallback）**：为兼顾本地交互与无头自动化，我们设计了 `OS Keyring → 环境变量 → 硬编码默认值` 的回退链。这一设计在 CI 中被充分验证：GitLab CI 的 Linux 容器内没有 D-Bus 钥匙串守护进程，`keyring` 会抛异常——回退链使代码从环境变量无缝读取凭据，在无界面容器中稳定运行 `unit-test`。**这说明「安全」与「自动化」并非对立，关键是回退语义要声明式并带明确错误提示，而非静默降级为明文文件。**

**Windows 本地开发环境的证书穿透**：开发期克服了 `UNKNOWN_CERTIFICATE_VERIFICATION_ERROR` 这一平台特色坑。复盘发现，Claude Code 底层由 Bun 编译器打包，其内置 BoringSSL 单独隔离管理证书、不读取 Windows 系统证书库——即便本地信任链完全正常仍报证书无法验证。最终注入环境变量 `"NODE_USE_SYSTEM_CA": "1"`，强行激活 Windows 内核级证书库信任成功穿透。教训：当工具链自带依赖树时，「系统级信任」不等于「应用级信任」，必须理解底层运行时如何装载证书。

## 6. 对 Superpowers 方法论的终极批判与重做反思 (Critical Reflections)

**Superpowers 假设的局限性**：Superpowers 隐含一个强假设——大模型能 100% 确定性执行指令。但真实世界反复证伪：网络 429 限流、401 鉴权失效、JSON 括号未闭合、LaTeX 编译器的各类物理报错，全都不是「指令执行」层面问题，而是「外部世界」强加的不确定性。若把方法论建立在确定性之上，系统首次遇到 429 或坏括号就会整体击穿。

**结论**：纯粹的 AI 方法论（Prompt、Skill、Agent）不够，必须叠加 Python 后端的工程防御才能搭建工业级应用。本项目沉淀的三道硬约束——**三重 JSON 防御**（正则粗解析 + 语法自愈重试 + 文件名降级兜底）、**指数退避重试**（`_call_with_rate_limit_backoff` 应对 429 限流）、**本地物理编译器沙盒探测**（实跑 xelatex 而非只做静态扫描）——共同构成「AI 不确定性与工程确定性」之间的缓冲带。方法论保证「想得对」，防御工程保证「做得稳」，二者缺一不可。

**如果重做会改变什么**：一是排版约束前置——从第一天就引入 `tabularx` 的 `lXXXX` 自适应折行与 `\geometry{margin=1.8cm}`，避免中期为修正固定列宽 `tabular` 溢出而做的整套重构；二是分发体验前置——早期即引入 `setup.ps1` 一键部署脚本，提升本地/CI/Docker 多环境一致性。这两项均属「早期成本极低、后期返工极高」的典型，应当前置而非延期。
